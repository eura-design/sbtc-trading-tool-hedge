# 1.  🔴 반드시 실거래로 확인 — 안 하면 돈이 걸린다
#############################################################

--- 1-1. 사전 손절이 진짜 발동하는가 ------------------------

  가장 중요하다. 이번 변경의 존재 이유가 이것이다.

  [ ] 지정가 주문을 내고 실제로 체결시킨 뒤,
      손절 가격까지 갔을 때 정말 청산되는가

  왜 코드로 확신할 수 없나:
    등록되는 것은 확인했지만, quantity 방식 트리거가 실제로
    발동해서 포지션을 닫는 것까지는 본 적이 없다.
    (지금까지 쓰던 closePosition 방식과 다른 주문 형태다)

  * ETH로 대신 확인 가능 -> 5번 E1


--- 1-2. 체결 직후 손절이 사라지는 순간이 있는가 -------------

  [ ] 지정가가 체결된 직후 바이낸스에서 손절이 계속 보이는가
      (체결 -> 5초 -> 30초 -> 1분 시점에 각각 확인)

  왜 위험한가:
    체결되면 onFilled가 "기존 알고 TP/SL 전부 취소 -> closePosition
    방식으로 재등록"을 한다. 그 사이 아주 짧게 손절이 없는 창이 생긴다.
    코드상 수백 ms지만 실제로 얼마나 되는지는 봐야 안다.

  이때 무방비 경보(빨간 배너)가 잘못 뜨는지도 같이 볼 것.
  (경보는 5초 뒤 재확인 후에만 뜨도록 되어 있어 안 떠야 정상)


--- 1-3. 백엔드를 끈 채로 체결시켜 보기 ----------------------

  [ ] 지정가 + 손절을 걸어두고 백엔드를 끈 다음,
      체결까지 기다렸다가 손절이 살아있는지 확인

  이번 변경의 최종 목표다. 1-1이 통과하면 이건 사실상 따라온다.
  급하지 않으면 건너뛰어도 된다.


--- 1-4. 진입 전에 익절이 먼저 발동하는 경우 -----------------

  [ ] 진입가 아래에 지정가를 걸고 익절을 현재가 가까이 둔 상태에서,
      가격이 익절선을 먼저 스치면 그 익절이 어떻게 되는가

  예상: 지킬 포지션이 없어 그냥 사라진다.
        -> 나중에 진입이 체결되면 익절 없는 포지션이 된다.
  확인할 것: 정말 조용히 사라지는지, 에러가 남는지, 취소로 기록되는지

  * ETH로 대신 확인 가능 -> 5번 E4


--- 1-6. 주인 없는 사전 TP/SL이 실제로 정리되는가 ------------

  [ ] 백엔드를 끈 채로 지정가를 체결시키고 손절까지 터뜨린 뒤
      백엔드를 켜면, 남아 있던 사전 익절이 1분 안에 사라지는가

  E2에서 발견한 문제를 고친 코드가 실제로 도는지 확인하는 항목이다.
  reconcile(60초)이 담당한다.
  콘솔에 "[RECONCILE] 주인 없는 사전 TP/SL → 취소" 가 찍히면 정상.


--- 1-5. 포지션이 닫힐 때 남은 주문이 정리되는가 -------------

  [ ] 손절이 발동해 포지션이 사라진 뒤,
      익절 / 추가진입 주문이 거래소에 남아있지 않은가

  남으면 나중에 원치 않는 포지션이 혼자 열릴 수 있다.
  (분할TP는 바이낸스가 자동 취소한다고 알려져 있지만
   quantity 방식 트리거도 그런지는 확인해야 한다)

  * ETH로 대신 확인 가능 -> 5번 E2

# 2.  🟡 확인하면 좋은 것
#############################################################

--- 2-1. 밖에서 낸 주문이 화면에 제대로 뜨는가 ---------------

  [ ] 바이낸스 앱/웹에서 지정가 진입      -> 차트에 "대기" 점선이 뜨는가
  [ ] 그 대기선의 x 를 눌러 취소되는가
  [ ] 바이낸스에서 분할 익절(지정가 청산) -> 분할 TP 목록/차트에 뜨는가
  [ ] 바이낸스에서 추가 진입(지정가)      -> 추가 진입 목록에 뜨는가
  [ ] 바이낸스에서 시장가 진입/청산       -> 즉시 반영되는가 (30초 아님)

  마지막 항목이 오늘 "늦게 뜬다"고 하신 부분이다.
  늦으면 아래를 확인:
      http://localhost:3002/api/health  ->  uds.connected 가 true인가
      uds.events 가 늘어나는가 / reconnects 가 늘어나는가


--- 2-2. 단일 TP와 분할 TP 공존 -----------------------------

  [ ] 분할 익절을 걸어둔 상태에서 차트의 +TP 를 끌어 단일 익절 등록
      -> 분할 익절이 안 지워지고 둘 다 남는가
  [ ] 반대로 단일 익절이 있는 상태에서 분할 익절 추가
      -> 단일 익절이 안 지워지는가
  [ ] 분할 익절이 먼저 체결된 뒤 단일 익절이 발동하면
      "남은 만큼만" 청산되는가 (합계가 포지션을 안 넘는가)

  마지막 항목이 이 변경의 핵심 전제다.


--- 2-3. 박스를 끌어 가격을 바꿀 때 --------------------------

  [ ] 미체결 상태에서 박스의 손절선을 드래그
      -> 거래소의 사전 손절 주문도 새 가격으로 바뀌는가
      (예전에는 파일만 바뀌어서 화면과 거래소가 갈라졌다)
  [ ] 박스의 진입선을 드래그 (주문 재등록)
      -> 옛 주문과 옛 사전 TP/SL이 남지 않는가


--- 2-4. 취소 경로 ------------------------------------------

  [ ] 플랜 카드의 "취소" -> 진입 + 사전 TP/SL 셋 다 사라지는가
  [ ] 밖에서 낸 주문이 같은 사이드에 있을 때 내 주문만 취소되는가
      (예전에는 그 사이드 진입 주문을 싹 취소했다)


--- 2-5. 부분 청산 -------------------------------------------

  [ ] 분할 익절이 여러 개인 상태에서 부분 청산
      -> 남은 분할 익절 수량이 잔여 비율대로 다시 걸리는가
  [ ] 밖에서 낸 분할 익절도 같이 재계산되는가 (오늘 추가된 부분)

# 5.  ETH 최소수량으로 대신 확인할 수 있는 것
#############################################################

  ETHUSDT 최소 주문금액은 20 USDT -> 0.009 ETH (약 $21.6)
  왕복 수수료 약 $0.017. 손실 위험은 스프레드 정도.

  주의: 우리 시스템은 BTCUSDT만 다루므로,
        ETH 테스트는 "바이낸스가 어떻게 동작하는가"만 확인한다.
        우리 라우트/화면 동작은 BTC로만 확인 가능하다.

  대신 BTC는 최소 0.001 = 약 $76이라 실제로 체결시켜 보기엔 크다.
  ETH면 $21로 "진짜 체결시키고 진짜 손절을 터뜨려" 볼 수 있다.
  1번 항목 대부분이 여기서 사실상 검증된다.


  E1. [완료 2026-08-23] 사전 손절(quantity 방식)이 실제로 발동하는가
      -> ✅ 발동해서 포지션을 청산했다.
         ETH 0.009 진입 -> STOP_MARKET(quantity) 트리거 -> 포지션 0.
         이번 변경(지정가 사전 TP/SL)의 핵심 전제가 실증됐다.
      ※ 트리거를 너무 가깝게(-0.01%) 걸면 "Order would immediately
        trigger"로 거절된다. 최소 간격이 있다.

  E2. [완료 2026-08-23] ⚠ 결과가 예상과 달랐다 — 자동 취소되지 않는다
      -> 포지션이 0이 된 뒤에도 익절이 status=NEW 로 살아남았다.
         분할 TP(지정가 reduceOnly)는 바이낸스가 자동 취소하지만
         **조건부 트리거 주문은 남는다.**
      -> 위험: 백엔드가 꺼진 사이에 체결·청산까지 일어나면 사전 익절만
         유령으로 남고, 나중에 같은 사이드에 새 포지션을 열었을 때
         엉뚱한 가격에 발동한다.
      -> 고침: reconcile(60초)이 "주인 없는 사전 TP/SL"을 취소한다.
         우리가 만든 id만 건드린다 (직접 걸어둔 예약 주문 보호).
      -> 남은 확인: 그 정리가 실제로 도는지 (아래 1-6)

  E3. [완료 2026-08-23] 포지션 없이 트리거가 발동하면 어떻게 되는가
      방법: 포지션이 하나도 없는 상태에서 롱·숏 × 손절·익절 4개를
            현재가 ±0.03%에 걸어, 어느 방향으로 움직여도 발동하게 함

      결과 -> **거래소가 REJECTED 처리하고 주문이 사라진다.**
         LONG 손절  (SELL/LONG  STOP_MARKET) : algoStatus=REJECTED
         SHORT 손절 (BUY/SHORT  STOP_MARKET) : algoStatus=REJECTED
         actualOrderId 없음 = **실제 주문이 만들어지지도 않았다**
         체결 없음 / 포지션 안 생김 / 반대 포지션도 안 열림

      뜻: 진입 전에 익절이 먼저 스쳐도 **돈을 잃지는 않는다.**
          유일한 결과는 "그 익절이 조용히 없어진다"이다.
          -> 체결됐을 때 익절 없는 포지션이 된다 (백엔드가 켜져 있으면 채워준다)

      ※ 실제로 발동을 본 것은 손절(STOP_MARKET) 두 개다.
        익절(TAKE_PROFIT_MARKET)은 트리거에 안 닿아 관측 못 했지만
        같은 조건부 주문이라 동작이 다를 이유가 없다

  E4. quantity 트리거와 closePosition 트리거가 공존 가능한가
      포지션이 있는 상태에서 둘을 같이 걸어본다
      -> -4130 같은 거절이 나는지 확인
      체결 직후 onFilled가 갈아끼우는 순간의 안전성과 관련

  E5. 포지션보다 큰 수량의 손절이 발동하면 어떻게 되는가
      0.009 진입 후 손절 수량을 0.018로 걸고 발동시킨다
